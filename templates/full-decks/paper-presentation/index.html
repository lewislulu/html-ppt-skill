背景 · 动机

细粒度锁不扩展

旧时代的方案

磁盘 I/O 主导执行时间，锁持有时间极短。细粒度锁足够好用。

现代硬件的现实

24+ 核 / 插槽，数据全在内存。每次获取读锁都会写入缓存行 → 所有核心的缓存副本失效 → 大量无意义的缓存缺失。

已有方案的困境

无锁：扩展性最好，极难实现。 HTM：需要特殊硬件。中间地带在哪里？

自适应节点类型

四种节点：Node4 → Node16 → Node48 → Node256，随条目增长自动升级。Node4 存 3 条目后再插入 2 个 → 升级为 Node16。

路径压缩

合并只有单子节点的路径，在节点头部存前缀字节。大幅降低树高，对长字符串尤其有效。

关键性质

ART 无重平衡操作。插入 / 删除最多影响 2 个节点（目标节点 + 父节点），比 B 树更适合锁耦合。

背景 · ART
协议一 · 乐观锁耦合

用版本号代替读锁

核心思想：读者不获取物理锁。快照版本号 → 乐观读 → 验证版本号未变。变了就重试。

// 乐观锁 = 锁标志位 + 版本计数器（同一原子变量） struct OptLock { std::atomic<uint64_t> lockVersion; // bit 0: 锁标志 | bits 1-63: 版本号 }; uint64_t readLockOrRestart(Node* n) { auto v = n->lockVersion.load(); if (v & 1) restart(); return v; } void readUnlockOrRestart(Node* n, uint64_t old) { if (n->lockVersion.load() != old) restart(); }

与传统锁耦合的差异

代码结构几乎相同。仅 readLock/unlock 替换为 readLockOrRestart/readUnlockOrRestart。可（几乎）像普通读写锁一样推理。

为什么能扩展

读者对共享缓存行零写入。版本号只读（共享态），不写（独占态）。缓存一致性流量大幅下降。

写者仍然用锁

写操作获取锁标志位。writeUnlock 递增版本号，触发看到中间态的读者重试。

OLC 对算法的三个要求

① 防止无限循环

读者在两个版本检查之间可能看到不一致状态。ART 树结构遍历不形成环，无此风险。

② 防止野指针

乐观读到的 nextNode 可能已被释放。解引用前加额外版本检查：checkOrRestart(node, version)。

③ 延迟内存回收

节点删除后不能立即释放。方案：epoch-based reclamation，标记 obsolete 后等所有读者离开 epoch。

前进保证：极端情况限制乐观重试次数，超限后降级为获取写锁。
调试技巧：将乐观原语映射到 pthread_rwlock，用 Helgrind 检测同步 bug，生产环境切回。

协议二 · ROWEX

读操作永不阻塞，永不重试

OLC 的弱点：所有操作都可能重试，高竞争下读性能恶化。ROWEX 消除读者重试 —— 零阻塞，零版本检查。

OLCROWEX
读者行为快照版本 → 乐观读 → 验证直接读，零开销
写者行为物理锁 + 递增版本本地锁 + 原子操作
代码改动最少 (≈44 行 lookup)需改数据结构内部
高竞争读退化保持稳定

核心权衡

ROWEX 中写者承担保证读者一致性的责任。不再由读者检测冲突（OLC 方式），而是写者通过原子操作和精心排序预防冲突。

与无锁方案的对比

ROWEX 比无锁容易，因为写者可以用锁（只是不对读者用）。比纯 CAS 设计有更多手段。但比 OLC 难 —— 必须修改数据结构内部。

适用场景：高竞争 + 读密集型。Zipf 偏斜度 = 3（83% 同一键），ROWEX 查找 ~22 Mops/s，OLC 降至 ~8 Mops/s。
协议二 · ROWEX
协议二 · 实现

让 ART 支持无阻塞读

局部修改：全部原子化

读者可见字段全部用 std::atomic：键字节 (N4/N16)、子索引 (N48)、子指针（全部）。x86 上原子读零额外指令，仅阻止编译器重排。

节点替换（4 步协议）

  1. 锁定节点 + 父节点
  2. 创建新节点，拷贝全部条目
  3. 原子写入父节点指针 → 新节点
  4. 标记旧节点 obsolete，解锁两者

路径压缩：level 字段技巧

安装新节点 + 截断前缀无法在一个原子操作内完成。读者可能看到中间态。解决：每个节点存一个 level 字段（创建后不变），读者用它检测并跳过不匹配的前缀。

实现细节

前缀 + 长度打包为单个 8 字节值 → 一次原子写入。代价：最大前缀从 9 字节降至 4 字节。

+12 字节/节点 (ROWEX) +8 字节 (OLC) +4 字节 (锁耦合)

竞争实验：Zipf = 3（83% 同一键）时 ROWEX 查找 ~22 Mops/s 保持平稳，OLC 降至 ~8 Mops/s，锁耦合崩至 ~2 Mops/s。ROWEX 非阻塞读的优势在此显现。
字符串实验：三种真实数据集。OLC / ROWEX 均接近无同步 ART。Masstree 随键变长缩小差距但仍落后。锁耦合在所有场景最慢。

总结

锁不邪恶。
滥用锁才邪恶。

① 乐观锁耦合 (OLC)

版本号替代物理读锁。仅 44 行 lookup。近无锁级扩展性。冲突少时首选。

② ROWEX

读者永不阻塞。写者用本地锁 + 原子操作。高竞争下读性能不退化。

③ 通用构建块

不是 ART 专用技巧。适用于 B 树、二叉搜索树等结构。两个协议都是实用中间方案。

真正的敌人不是锁 —— 是不必要的共享缓存行写入。OLC 和 ROWEX 都消除了读者的缓存行写入。需要简单选 OLC，需要读决不等待选 ROWEX。不要抛弃锁 —— 少量、谨慎地使用它。
